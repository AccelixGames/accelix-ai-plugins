# Presend Tone — 사전 확인 메시지 톤 룰

**디자인허브 적용 사전 확인 메시지(`/design-send-pre`)는 자연어 톤으로 작성. 시스템 보고서 톤·spec 내부 용어 그대로 던지기 금지.**

## 배경

2026-05-13 wish-pool-jegal 사전 확인 첫 송신 후 플머 피드백: "전혀 요청을 못 알아먹겠다." 원인:

- spec 내부 용어 그대로 (`commonDialogueOverrides`, `immediateFullfillmentDialogue`, `unlockConditional`, `ValueProvider sourceType`)
- 코드 약어와 spec 약어 혼재 (`SO_WishPool`, `F_AS/F_BR/F_JU`)
- 자연어 설명 없음, 곧장 기술 질문
- 선택지 나열만, 기획자 의견 없이 옵션만 던짐
- 시스템 보고서 톤 (기획자 → 플머 부탁/협업 어조 아님)

## 본문(요약) 톤 룰

### 1. 제목

`[{spec-id}] 사전 확인 요청 — {spec 한국어 이름}` (spec 한국어 이름 포함, 플머가 즉시 파악)

### 2. 3단 구조 필수

- `**작업하려는 것**`: 자연어 1~2문장. "무엇을 박으려고 한다"
- `**제가 진행할 부분** (보고)`: 기획자 자기 권한으로 진행하는 항목. 플머에게 OK 묻지 않음. 단순 보고/공유.
- `**막힌 부분** (이건 답이 있어야 진행 가능)`: 문의 항목, 각 항목에 배경+예시+구체 질문

### 3. 자기 권한 vs 문의 구분 룰

- **진행 가능한 것을 진행하는 것은 기획자(사용자)의 권한**. 플머에게 OK 받지 않음.
- "진행해도 괜찮을까요?", "이거 진행해도 OK?" 류 부탁/허락 어조 금지.
- 플머에게 묻는 건 **막힌 부분에만**.

### 4. Claude 자체 의견/판단 금지

- "저는 ~ 쪽이 좋아 보입니다" 같은 기획자 시점 의견을 Claude가 임의로 만들지 말 것.
- 기획자 의견은 **사용자가 명시적으로 제공한 경우에만** 본문에 추가.
- 사용자 명시 안 했으면 질문만 던지고 끝. Claude의 추정·선호·우려는 본문에 X.

### 5. 약어 풀어쓰기

- `F_JU` → "착즙기 가구"
- `commonDialogueOverrides` → "공통 가구 소망을 메이드별 톤으로 말하게 하는 구조"
- `SO_WishPool` → "Wish 시스템 풀 데이터" 또는 "(Pool) ___.asset"

### 6. 예시 1개씩 첨부

막힌 부분 각 항목에 spec/코드 1줄 인용 또는 비유 1개 (메이드 톤 예시 등 자연어 인용도 좋음)

### 7. 부탁/협업 어조 (막힌 부분 한정)

- 평어, 짧은 문장
- "...해주실 수 있을까요?" / "...어떻게 처리하는지 알려주시면" / "...진행 단계 공유해주시면"
- "어떻게 할까요?" 식 모호 질문 금지 → "X로 하면 됩니까, Y로 하면 됩니까?" 식 구체

## 첨부 md(상세) 톤 룰

- 본문보다 자세하게, 단 톤은 동일 (자연어, 풀어쓰기)
- 섹션: `## 배경`, `## ProjectMaid 측 매핑`, `## 제가 진행할 부분`, `## 막힌 부분`, `## 부수 (locale 등)`, `## 요청 요약`
- 각 막힌 부분에 코드 인용 + 자연어 해설 함께
- 기획자 시점 명시 (사용자가 제공한 경우만)

## 검증 체크리스트 (송신 전 자가 점검)

- spec 약어 풀어 쓴 곳이 있나?
- 한국어 풀어쓰기가 본문에서 7할 이상 차지하나?
- 막힌 부분 각 항목에 예시 1개씩 있나?
- 시스템 보고서 톤이 남아있지 않은가?
- "진행해도 될까요?" 류 부탁/허락 어조가 진행할 부분에 들어가 있지 않은가? (자기 권한이라 보고만)
- Claude 자체 의견(추정/선호/우려)을 임의로 본문에 넣지 않았는가? (사용자 명시한 경우만 의견 추가)
